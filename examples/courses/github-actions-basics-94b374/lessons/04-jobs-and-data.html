Lesson 4 · Job graph

Connect work without assuming a shared machine.

Jobs can run in parallel, wait for one another, and exchange selected data. Those boundaries make a workflow faster and easier to reason about.

Add dependencies only where they are real

Jobs run independently unless needs adds a job dependency. A deployment that consumes a tested build should wait for the build. Linting and unit tests often have no reason to wait for each other.

Example: fan out and join

test and lint start together. A deploy job with needs: [test, lint] starts only after both succeed.

Choose the data mechanism by what crosses the boundary

NeedMechanism
Value for a later step in the same job$GITHUB_OUTPUT or $GITHUB_ENV
Small value for another jobJob output
Files for another job or later inspectionArtifact
Faster repeated dependency workCache
Example: pass a version and a built site

The build job exposes version 1.4.0 as a job output and uploads dist/ as an artifact. A cache would speed up repeated setup instead of preserving that deployable result. The deploy job reads the small value and downloads the exact files.

Use a matrix for systematic variants

A matrix expands one job definition into several jobs. Use it when the commands stay the same but an input such as operating system or language version changes.

Example: test two Node versions

matrix.node: [22, 24] creates two test jobs. Each job uses ${{ matrix.node }} during setup, so the same test sequence checks both runtimes.

Do not confuse cache with result storage. Cache makes recomputation faster. An artifact preserves the files a later job or person needs.
