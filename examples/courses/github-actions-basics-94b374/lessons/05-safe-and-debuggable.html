Lesson 5 · Operations

The job graph now runs the right work and moves the intended data. Before trusting it, account for what else enters the run: repository permissions, forked code, issue text, third-party actions, and failures outside GitHub.

Limit power and make failures explain themselves.

A pull request from a fork changes both code and a title that the workflow inserts into a shell command. The job also has permission to write releases even though it only runs tests. One careless string or compromised action now has more power than the task needs.

Treat workflow inputs as untrusted, grant the job only the permissions it needs, and leave evidence at each layer so a failure can be located without guesswork.

Grant the built-in token only what the job needs

Declare permissions for the built-in job token instead of relying on a broad default. Start with no permission or read-only repository contents, then add a specific write permission only to the job that performs that operation.

Example: tests only read the repository

A test job uses permissions: { contents: read }. It can check out the code but cannot create releases or modify issues with its built-in token.

Treat outside values and code as untrusted

Pull request titles, branch names, issue text, forked code, artifacts, and caches may be attacker-controlled. Pass text as quoted data instead of inserting expressions into shell source. Review third-party actions and pin sensitive workflows to verified commit SHAs.

Example: keep a title out of shell source

Put the pull request title in an environment variable and pass the quoted variable to a program. Do not paste the title expression directly into a shell command where punctuation could become syntax.

Debug from trigger to side effect

Ask four questions in order: Was a run created? Did the job schedule? Which step failed? Did the external system perform the intended change? This separates trigger mistakes from runner, command, permission, and provider failures.

Example: a job waits without starting

The run exists, but the job remains queued. Inspect its runner label and availability before changing the shell command, because no step has executed yet.

Run
Event and filters matched.
Job
Dependencies passed and a runner accepted it.
Step
The command or action returned a result.
Side effect
The target system changed as intended.

Put evidence near the failure. Use clear names, timeouts, concise summaries, and uploaded reports so the next person can identify the failed layer quickly.
