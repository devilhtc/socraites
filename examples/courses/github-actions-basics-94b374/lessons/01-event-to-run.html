Lesson 1 · Mental model

Follow one event all the way to a result.

GitHub Actions is easier to read when you can name what selects the automation, what groups the work, and where each command runs.

GitHub's overview follows a workflow through build, test, and deployment. As you watch, identify the event, each job, and the runner that executes it.

The workflow starts with an event

A workflow is a YAML file in .github/workflows/. Its on section selects events such as a push, a pull request, or a manual request. When an event matches, GitHub creates a workflow run from that committed file.

Example: a pull request starts CI

A contributor opens a pull request. A workflow containing on: pull_request matches the event, so GitHub creates a run and shows its result as a check on the pull request.

Jobs are the units sent to runners

A workflow contains one or more jobs. Each job runs on one runner, which is the machine executing the work. Jobs without dependencies may run in parallel. Separate jobs do not automatically share a filesystem.

Example: test and lint can overlap

A workflow defines test and lint jobs with no dependency between them. GitHub can assign each job to a different hosted runner and execute both at once.

Steps run in order inside a job

A step either runs a shell command with run or invokes a reusable action with uses. Steps in one job share the runner's workspace and execute from top to bottom.

Example: checkout must come before tests

actions/checkout puts the repository files on the runner. A later run: npm test step can then read them. Reversing those steps would ask the test command to run before the code exists on that runner.

  E[Matching event] --> W[Workflow run]

  J1 --> R1[Runner]
  J2 --> R2[Runner]
  R1 --> S1[Ordered steps]
  R2 --> S2[Ordered steps]

Read from outside to inside. Event selects workflow, workflow contains jobs, each job gets one runner, and that runner executes the job's steps in order.
