Lesson 3 · Triggers

Run the right workflow at the right time.

The best job definition is useless if its event never matches. Choose the trigger from who or what should start the work.

Use repository events for repository activity

push, pull_request, and release react to activity GitHub already knows about. Pick the event whose payload and timing match the work, not merely the event that is easiest to remember.

Example: test before merge

Use pull_request for checks that should update as a proposed change evolves. Use a filtered push to run a separate check only after commits land on main.

Use manual triggers for operator choices

workflow_dispatch lets a person or API start one named workflow. It can accept inputs such as a target environment. A schedule is better for periodic work that does not need an operator at the keyboard.

Example: choose a deployment target

An operator starts deploy.yml from the Actions tab and selects staging. The workflow reads that typed input instead of guessing the target from a branch name.

Filters remove runs before jobs exist

Branch, tag, path, and activity filters narrow an event. If no run appears, inspect the on block and its filters first. Runner and step logs cannot explain a run that GitHub never created.

Example: a path filter explains missing CI

A workflow only includes src/**, but a pull request changes docs/guide.md. GitHub does not create the run because the changed path does not match.
