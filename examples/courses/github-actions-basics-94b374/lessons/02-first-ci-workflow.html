Lesson 2 · First workflow

Turn a small YAML file into repeatable CI.

A useful first workflow checks every pull request and main-branch push with the same install and test commands.

Put the file where GitHub looks

Create .github/workflows/ci.yml. The filename is for humans; the keys inside define the workflow's display name, triggers, permissions, and jobs.

Example: two workflow files stay independent

ci.yml can test each change while release.yml publishes tagged releases. Both live under .github/workflows/, and each declares its own triggers and jobs.

Connect each YAML key to behavior

name: CI

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with:
          node-version: 22
          cache: npm
      - run: npm ci
      - run: npm test

runs-on selects the runner image. The two uses steps reuse actions for checkout and Node setup. The run steps execute project commands. The timeout prevents a stuck job from running forever.

Example: a failed test stops the job

If npm test exits with a nonzero status, the step and job fail. GitHub reports the failed check on the pull request so the author can open its logs.

Prove the workflow by observing it

Push the file to a disposable repository. Open the Actions tab, inspect the job and step list, then deliberately break one test. The failed run teaches more than reading the YAML alone.

Example: a safe first experiment

Add an assertion that is known to fail, push it, and find the exact failing command in the run log. Restore the assertion, push again, and confirm that the new run passes.

A workflow should reproduce a local check. Start with commands the project already uses, then automate them on a clean runner.
